# 안내형 문진 위저드 (guided-intake-wizard) — 요구사항

작성: 2026-08-13. 사용자와의 설계 대화에서 확정된 내용.
선행 문서: `docsPlan/ai-token-speed-accuracy/DECISION.md`(속도·토큰·정확도 종합 결정안).

이 트랙은 DECISION.md의 **트랙 2(임상 추론 루프)** 를 대체·구체화한다. DECISION.md는
"질문 주도 대화(채팅 UI 유지)"를 상정했으나, 설계 대화에서 **채팅 형태 자체를 버리고
양식·위저드 형태로 간다**고 방향이 바뀌었다. 근본 원칙("상태·채점은 JS, LLM은 얇게")은
그대로 유지된다.

---

## 1. 배경 — 왜 만드는가

현재 메인 화면(`index.html`)은 채팅 UI다. 상담사가 소견을 자유 서술하면 AI가 여러 턴에
걸쳐 응답한다. 두 가지 문제가 실측됐다.

| 문제 | 원인 (DECISION.md에서 실측 확인) |
|---|---|
| 느림 | 매 턴마다 "기준 전문 + 그때까지의 전체 대화"를 다시 통째로 AI에 보냄. 한 번 결과를 보려면 AI 호출이 최대 6회 |
| `(ABORT)` 크래시 | 위 구조 때문에 보내는 양이 계속 늘어나 문맥 한도(N_CTX=4096)를 초과 |

응급 가드(`js/context-budget.js`, 2026-07-19)는 증상 억제일 뿐 구조를 바꾸지 않았다.
**AI 호출 횟수와 프롬프트 크기를 구조적으로 줄이는 것**이 이 트랙의 목적이다.

## 2. 이 도구의 성격 (설계의 전제)

**내담자가 직접 입력하는 자가진단 도구가 아니다.** 상담사가 내담자를 관찰하거나
보고받은 내용을 바탕으로 **상담사 자신이 판단해서 체크하는 임상 보조 기록 도구**다
(SCID 구조화 임상면담과 같은 위치).

따라서 모든 질문 문구는 "내담자에게 그대로 읽어주는 문항"이 아니라
**"상담사가 판단해서 답하는 문항"** 으로 작성한다.

이 도구가 하는 일 / 하지 않는 일:

- 한다 — 81개 진단 기준을 빠짐없이 짚어주는 회상 보조, 기준 충족 여부 자동 계산, 문서화
- 하지 않는다 — 증상의 유무 판정, 자기보고 신뢰도 평가, 의학적 원인 감별, 최종 진단

## 3. 전체 흐름

```
[0] 소견 입력 (선택)      상담사가 1~2문장으로 대략의 소견 입력
        ↓ JS 키워드 매칭 (AI 아님, 0초)
[1] 게이트 위저드          질문 1개씩 화면에 표시 → 예/아니오/모름 클릭 → 자동으로 다음
                          약 21~23문항, 관련 높은 순서로 정렬됨
        ↓ JS 판정 (AI 아님, 0초)
[2] 정밀 체크리스트        "예/모름"으로 걸린 범주만 자동 펼침
                          (기존 checklist.html 로직 재사용)
        ↓ JS 채점 (AI 아님, 0초)
[3] 결과 + AI 설명         채점 결과 즉시 표시 + "AI 설명 받기" 버튼 → AI 호출 1회
```

**AI 호출은 [3]단계에서 딱 1회.** [0]~[2]는 전부 결정론적 JS다.

## 4. 단계별 요구사항

### 4.0 소견 입력 (선택 사항)

- 상담사가 1~2문장 정도의 대략적 소견을 입력할 수 있다. **건너뛸 수 있다.**
- 입력된 문장에서 JS가 키워드를 매칭해 **게이트 질문의 순서를 재배열**한다.
- **완전 배제는 하지 않는다** — 관련 낮은 범주는 뒤로 밀릴 뿐 사라지지 않는다.
  (키워드가 틀렸을 때 해당 진단이 통째로 안 보이게 되는 false negative 방지)
- 매칭 근거를 화면에 표시한다. 예: "'불면·무기력'을 감지해 우울장애·수면-각성장애를
  앞으로 배치했습니다." 상담사가 그 자리에서 순서·포함 여부를 직접 고칠 수 있다.

### 4.1 게이트 위저드

- **한 화면에 질문 1개.** 답변 버튼을 클릭하면 별도의 "다음" 버튼 없이 자동으로 넘어간다.
- 진행률을 표시한다 (예: `12 / 23`).
- **답변은 3상태: 예 / 아니오 / 모름(확인 안 됨).**
  - "모름"을 "아니오"로 취급하지 않는다. 확인하지 못한 것과 없는 것은 다르다.
- **"아니오"도 완전 배제가 아니다.** 해당 범주는 후순위로 밀리되, 결과 화면 하단에
  접힌 상태로 여전히 접근 가능하다. (실제 임상가도 게이트 하나로 완전 배제하지 않는다)
- 이전 질문으로 돌아가 답을 고칠 수 있다.
- **모든 게이트 질문을 순회한다** — 중간에 건너뛰고 바로 결과로 가는 기능은 넣지 않는다
  (정확도 우선. 대신 4.0의 순서 재배열로 체감 시간을 줄인다).

### 4.2 게이트 질문의 단위와 출처

- **단위**: 18개 대범주가 기본이되, 범주 안에 성격이 이질적인 진단이 섞인 경우
  **DSM이 이미 나눠둔 하위 묶음 단위**로 쪼갠다. 총 약 21~23문항.

  | 범주 | 게이트 수 | 근거 |
  |---|---|---|
  | 성격장애 (10개 진단) | 3 | DSM A군(편집성·조현성·조현형) / B군(반사회성·경계성·연극성·자기애성) / C군(회피성·의존성·강박성) |
  | 신경발달장애 (7개 진단) | 3 | 발달·지적(지적발달장애·특정학습장애) / 사회성·상동(자폐스펙트럼·상동증적 운동장애) / 주의·운동(ADHD·발달성 협응장애·뚜렛장애) |
  | 나머지 16개 범주 | 각 1 | 범주 내 진단들이 핵심 증상을 공유함 |

  범주에 게이트가 여러 개면 **OR 판정** — 하나라도 예/모름이면 그 범주로 진입한다.

- **출처(기본)**: 새로 창작하지 않는다. 각 진단의 `groups[0].items[0]`(+필요시 `items[1]`),
  즉 **data.js에 이미 있는 항목 중 가장 핵심적인 것**을 질문형으로 바꿔 쓴다.
  DSM은 통상 핵심 증상을 항목군 맨 앞에 배치하므로 이 규칙이 성립한다.
  이 방식은 검증 대상 콘텐츠를 새로 늘리지 않는다(기존 data.js와 동일한 리스크).
- **검증 상태**: data.js 자체가 "AI가 재서술한, 임상 전문가 미검증" 콘텐츠다
  (README 명시). 게이트 질문도 같은 리스크를 가지며, 화면에 경고 문구를 유지한다.

### 4.3 정밀 체크리스트 단계

- 게이트에서 "예/모름"으로 걸린 범주의 진단들이 **자동으로 펼쳐진 상태**로 표시된다.
- "아니오" 범주는 하단에 접힌 채로 남는다 — 필요하면 상담사가 펼칠 수 있다.
- 채점 로직은 기존 `js/main.js`의 `groupSatisfied` / `diagnosisScore`와 **동일한 규칙**을
  쓴다(항목군 min, groupLogic AND/OR).
  **주의(2026-08-13 코드 확인)**: `main.js`는 전체가 IIFE로 감싸여 있고 외부에 아무것도
  노출하지 않아 이 함수들을 파일 밖에서 호출할 수 없다. "그대로 재사용"은 불가능하며,
  채점부를 순수 모듈(`js/scoring.js`)로 **추출**해야 한다 → main.js 수정 불가피
  (checklist.html 회귀 위험 발생, R10 참조).
- **미체크 항목을 "없음"으로 표시하지 않는다.** 결과에 "확인된 항목 N개 / 미확인 M개"
  형태로 구분해 보여준다 — 안 물어본 것이 조용히 "증상 없음"으로 처리되는 것을 막는다.

### 4.4 결과 + AI 설명

- 채점 결과(기준 충족 / 부분 일치 %)는 **AI 없이 즉시** 표시된다.
- "AI 설명 받기" 버튼을 누르면 **AI 호출 1회**로 진단명과 근거 설명을 서술받는다.
  - AI에 보내는 것: 좁혀진 후보 진단 + 체크된 항목(근거) + 기간·배제기준
  - AI에 보내지 않는 것: 81개 진단 전체 사전, 대화 이력(대화 자체가 없음)
  - **프롬프트 크기 상한을 반드시 둔다** — 1회 호출이어도 후보가 10개 이상 걸리면
    프롬프트가 커진다. 상한: 후보는 **상위 N개만**(N은 structure.md에서 확정, 기본 5),
    각 진단은 **체크된 항목만** 싣고 기준 전문은 싣지 않는다. 조립 후 토큰 근사치를
    `context-budget.js`로 재확인한다.
- **AI는 판단·계산·좁히기를 하지 않는다.** 이미 확정된 결과를 사람이 읽기 좋은 문장으로
  서술하는 역할만 한다.
- **AI를 안 써도 도구는 완전히 작동한다** (AI는 선택적 보조). 이 원칙은 4.6의
  파일 배포 시나리오와 직결된다.
- 결과는 기존과 같이 `.txt`로 내보낼 수 있다.

### 4.5 진행 상태 보존

- **sessionStorage**에 저장한다 — 새로고침·뒤로가기해도 이어서 진행 가능.
  탭을 닫으면 자동 소멸한다.
- **localStorage는 쓰지 않는다** — 내담자 증상 정보가 컴퓨터에 계속 남으면
  공용 PC에서 위험하다. "어제 하던 상담 오늘 이어서"는 지원하지 않는다(의도적 제외).
- 화면에 **"처음부터 다시"** 버튼을 둬서 상담사가 언제든 지울 수 있게 한다.
- 저장 대상: 소견 문장, 게이트 답변, 진행 위치, 체크된 항목.

### 4.6 배포 형태 — 웹 접속이 기본

| 방식 | 위저드·채점·저장 | AI 설명 | 멀티스레드 속도 |
|---|---|---|---|
| 웹 접속 (기본) | 작동 | 작동 | 작동 |
| 파일 다운로드 후 직접 열기 | 작동 | **불가** | 불가 |

파일로 직접 열면 브라우저가 `file://` 페이지를 "출처 불명"으로 취급해 ES 모듈 로드와
외부 CDN 요청(wllama 엔진·1.4GB 모델)을 차단한다. 이는 브라우저 보안 정책이라
우회 대상이 아니다.

→ **설계 결론**: 위저드 코드는 `main.js`처럼 **일반 스크립트(비-module)** 로 작성해
파일 배포에서도 핵심 기능이 살아있게 한다. AI 연동만 module로 분리한다(§ structure.md).

웹 접속이어도 내담자 정보는 서버로 전송되지 않는다(정적 사이트 + 브라우저 내 추론).

## 5. 기존 기능 처리

- **채팅 UI는 삭제하지 않는다.** `index.html`에서 떼어내되 `chat.html`로 옮겨 보존한다.
  위저드에 문제가 생기면 즉시 되돌릴 수 있고, 기존 코드 회귀 위험이 사실상 없다.
- `checklist.html`(81개 전체 브라우징)은 그대로 유지 — "어디를 볼지 이미 아는" 숙련자용.
- `js/context-budget.js`는 삭제하지 않는다 — chat.html 경로에서 여전히 유효하고,
  위저드의 1회 호출 경로에도 안전망으로 태운다.

## 6. 성공 판정 기준

| 항목 | 기준 |
|---|---|
| 크래시 | 위저드 전 과정에서 `(ABORT)` 0회 (누적 대화가 없으므로 구조적으로 발생 불가) |
| AI 호출 횟수 | 결과 1건당 1회 (현재: 최대 6회 × 대화 턴 수) |
| 프롬프트 크기 | 후보 수에 비례하며 대화가 길어져도 커지지 않음 |
| 소요 문항 수 | 게이트 21~23문항 + 걸린 범주의 정밀 항목만 |
| AI 없이 사용 | AI를 한 번도 호출하지 않고 결과 도출·저장까지 완주 가능 |

**주의**: "한 번의 AI 응답이 나오는 속도(토큰/초)"는 이 트랙의 범위가 아니다.
그것은 DECISION.md 트랙 B(coi-serviceworker 멀티스레드)가 담당하며,
2026-07-19 구현·배포됐으나 실배포 체감 속도는 아직 미실측 상태다.

## 7. 범위 제외 (이번에 하지 않는 것)

- 게이트 질문의 임상 전문가 검증 (자문 확보 시 별도 진행)
- **APA 공식 평가도구 문항 도입** (§8 후속 결정 사항)
- 접근 제한·인증 (§8)
- ICD-11 이중 대조
- 내담자 직접 입력 모드
- 여러 날에 걸친 상담 이어하기 (localStorage 미사용 결정에 따름)
- AI 응답 속도 자체의 개선 (별도 트랙)
- 파일 배포용 런처(로컬 서버 자동 실행) 제작

## 8. 후속 결정 사항 — APA 공식 문항 도입 검토

2026-08-13 조사에서 확인된 사실:

- APA가 **DSM-5-TR Level 1 Cross-Cutting Symptom Measure**를 무료 공개하고 있다.
  성인용 **13개 영역 / 23문항**, Level 1(스크리너) → Level 2(심층)의 2단계 구조로,
  본 트랙의 "게이트 → 정밀 체크리스트" 설계와 발상이 동일하다.
- 허용 문구(원문): *"This material can be reproduced without permission by researchers
  and by clinicians for use with their patients."*
- **쟁점**: 이 허용은 "연구자·임상가가 자기 환자에게 사용"으로 한정된다. 개별 상담사의
  사용은 명백히 허용이나, **웹앱에 담아 재배포**하는 것이 이 범위에 들어가는지는 불명확.
  APA 허가 창구(appi.org/Support/Customer-Information/Permissions)에 문의하면
  명확한 답을 얻을 수 있는 종류의 문제다(data.js의 회색지대와 달리).

**지금 당장 쓸 수 있는 것 / 없는 것**:

- 쓸 수 있음 — Level 1의 **구조**(어떤 영역들을 스크리닝 대상으로 삼는지, 2단계 설계).
  사실 정보라 저작권 대상이 아니며, §4.2의 게이트 묶음 설계에 참고 가능.
- 도입 보류 — **문항 문구 자체**. APA 문의로 배포 조건이 확인된 뒤에 결정한다.
  도입되면 검증된 문항이므로 R9(문구의 임상적 부정확) 리스크가 크게 해소된다.

**국내 출판 평가 문항집**: 검토했으나 제외. 명시적 재배포 허용 문구가 붙는 경우가
드물고, 척도 문항은 짧아 재서술해도 원문과 유사해지기 쉬워 오히려 리스크가 크다.

### 8.1 접근 제한 — "상담사에게만 제한적으로 공개" (2026-08-13 사용자 결정)

사용자 요구: 불특정 다수가 아니라 **내담자를 위해 쓰려는 상담사에게만** 열고 싶다.

조사 결과(2026-08-13):

| 방식 | 실제 차단력 | 비용·제약 |
|---|---|---|
| 클라이언트 비밀번호 | **없음** — 소스 보기로 노출 | 무료. 보안이 아니라 "일반 대중용 아님"의 의사표시 수준 |
| GitHub Pages 비공개 게시 | 있음 | **불가** — GitHub Enterprise Cloud 조직 전용 기능. 개인 계정·Pro로는 안 됨 |
| Cloudflare Pages + Cloudflare Access | **있음(진짜 인증)** | Zero Trust 무료 플랜 **50명까지 $0**. 이메일 OTP 등 IdP 인증. 호스팅을 GitHub Pages → Cloudflare Pages로 이전 필요 |
| 파일로 직접 전달 | 있음(배포 자체를 제한) | AI 기능 불가(§4.6) |

**결정(2026-08-13, 사용자)**: **공개 배포 유지 + 링크 선별 안내 + 경고 문구**로 간다.
Cloudflare 이전은 하지 않는다(보류).

근거 — APA의 "임상가가 자기 환자에게" 조건은 **APA 문항을 실제로 도입할 때만**
구속력을 갖는다. 이번 트랙의 게이트 질문은 data.js에서 도출하므로(§4.2) 저작권 리스크가
기존 앱과 동일하며, 호스팅 이전이라는 큰 공사를 지금 감행할 이유가 없다.
Cloudflare Access 무료 한도(50명)도 지금 규모에선 판단하기 이르다.

이번 트랙에서 실제로 하는 것:

1. `noindex` 메타 태그 — 검색엔진 색인 차단(한 줄, 비용 0). 우연한 유입만 막는다.
2. **첫 화면 경고 문구** — "상담·임상 전문가가 내담자를 위해 사용하는 도구이며
   일반인의 자가진단용이 아님" + 기존 README의 "DSM-5-TR 비공식·미검증" 고지.
3. **결과 `.txt` 내보내기에도 같은 문구** — 파일만 따로 돌아다닐 수 있으므로.
4. 링크를 공개적으로 홍보하지 않는다.

이는 기술적 차단이 아니라 **용도 표시**임을 명확히 인지한 상태의 결정이다.

**보류안(참고용)**: Cloudflare Pages + Access(무료 50명)는 서버를 직접 운영하지 않으면서
진짜 인증을 걸 수 있는 유일한 현실적 선택지다. 인증은 페이지 접근 앞단에서만 일어나므로
"서버 없음 = 내담자 정보 유출 경로 없음"이라는 장점도 유지된다. APA 문항 도입을
결정하는 시점에 이 카드를 다시 검토한다.

**부수 효과(확인 필요)**: 저장소 루트의 `_headers` 파일은 원래 Cloudflare/Netlify 규약인데
GitHub Pages가 무시해서 무용지물이었다(DECISION.md에서 curl로 실측). Cloudflare Pages는
이 파일을 인식하므로 **COOP/COEP 헤더가 진짜로 적용**되어, `coi-serviceworker` 우회 없이
멀티스레드가 켜질 가능성이 있다. 이전 시 실측할 것.

**부수 효과가 아까운 점**: 위 `_headers` 이득(멀티스레드)은 보류안을 채택할 때만
따라온다. 다만 그것은 속도 트랙(DECISION.md 트랙 B)의 관심사이지 이 트랙의 범위가
아니므로, 이번 결정에 영향을 주지 않는다.
